## How work moves
 
Work moves in one direction: doctrine, then implementation. A request
becomes a decision becomes a verified change becomes a record. It does
not skip steps under pressure. Discipline over speed is Sacred Rule 4.
 
## The loop
 
1. **Request** — the Owner/Operator or a client raises a need.
2. **Read the terrain** — the relevant agent identifies what is
   reversible, what is not, and what it depends on.
3. **Decide or escalate** — if the call is within an agent's
   canonical ownership it is made; if it is a founder decision it is
   escalated with sources, not a recommendation dressed as fact.
4. **Sandbox** — the change is built and verified somewhere it cannot
   break production.
5. **Ship** — one change per deploy where possible, with a
   verification step a human can see.
6. **Record** — the change leaves an audit trail. The standing ledger
   names what is now open, deferred, or blocked.
 
## What never happens
 
- No irreversible operation runs through automation.
- No "shipped" or "verified" claim without a visible verification.
- No disagreement is buried. It is surfaced via the bus pattern with
  both sides intact and the Owner/Operator decides.
- No implementation redefines doctrine. When a request would, the
  agent says so plainly rather than complying quietly.
 
## Cadence
 
Per-batch review is the default for documentation and multi-file
work: build a coherent batch, review it in place, then the next
batch. One change per deploy is the default for code. The cadence
exists so the real bottleneck stays visible instead of being buried
under parallel motion.
 
## The ledger discipline
 
Every turn of substantial work, the open threads are named, oldest
first. Deferred is not forgotten — it is governed uncertainty held
intentionally until there is enough operational truth to resolve it.
Naming what is deferred is how the system stays honest about its own
state.
